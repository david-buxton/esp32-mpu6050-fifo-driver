# ESP32 MPU6050 Interrupt-Driven FIFO Acquisition

## Overview

An interrupt-driven accelerometer acquisition driver for the MPU6050, developed in C using ESP-IDF and FreeRTOS.

The project implements direct register-level communication over I2C, hardware FIFO buffering, interrupt-driven task notification, batch sample acquisition and FIFO overflow recovery.

The objective is to demonstrate an efficient sensor acquisition architecture without relying on an existing MPU6050 driver library.

## Features

- Direct register-level I2C communication.
- Device identification and configuration.
- Configurable accelerometer sampling rate.
- Hardware FIFO buffering.
- GPIO interrupt handling.
- FreeRTOS task notifications from an ISR.
- Batch acquisition of up to 32 three-axis samples.
- Signed 16-bit accelerometer data decoding.
- FIFO overflow detection and recovery.
- Error handling using ESP-IDF return codes.
- Compile-time selection of hardware integration tests.

## Acquisition Architecture

1. The MPU6050 samples accelerometer data at 100 Hz.
2. Three-axis accelerometer samples are written into the hardware FIFO.
3. A data-ready interrupt is generated by the MPU6050.
4. The ESP32 GPIO interrupt service routine notifies the FreeRTOS acquisition task.
5. The acquisition task checks for FIFO overflow.
6. Available complete samples are read in batches of up to 32 samples.
7. Raw bytes are decoded into signed 16-bit X, Y and Z readings.
8. The acquisition task returns to a blocked state once all complete samples have been drained.

The ISR performs minimal processing, with I2C communication and data handling deferred to task context.

## Sampling and FIFO Configuration

| Parameter | Value |
|---|---|
| Sampling frequency | 100 Hz |
| Accelerometer filter bandwidth | 44 Hz |
| Bytes per sample | 6 |
| FIFO capacity | 1024 bytes |
| Data generation rate | 600 bytes/s |
| Approximate FIFO fill time | 1.7 seconds |
| Maximum batch size | 32 samples |
| Maximum batch payload | 192 bytes |
| Acquisition task stack | 4096 bytes |

Batch acquisition allows the driver to drain accumulated samples efficiently following delays in task execution.

## Building and Running

With ESP-IDF installed and configured, run the following commands from the project root:

```bash
idf.py set-target esp32
idf.py build
idf.py flash monitor
```

## Hardware Integration Tests

Tests are selected at compile time by modifying `ACTIVE_TEST` in `test_acquisition.h`.

| Test definition | Purpose |
|---|---|
| `TEST_ACCEL_READING` | Check accelerometer readings, range and sensitivity |
| `TEST_FIFO_ACCUMULATION` | Verify FIFO accumulation over 500 ms |
| `TEST_FIFO_DRAIN` | Verify FIFO burst reading and remaining byte count |
| `TEST_FIFO_OVERFLOW` | Induce FIFO overflow and observe recovery |
| `TEST_NONE` | Normal interrupt-driven acquisition |

For example, to run the FIFO overflow test:

```c
#define ACTIVE_TEST TEST_FIFO_OVERFLOW
```

Rebuild and flash the firmware after changing the test selection.

The overflow test deliberately suspends the acquisition task for three seconds, allowing the hardware FIFO to fill and overflow. The acquisition task is then resumed to exercise overflow detection and recovery.

Test results are inspected manually through the serial monitor.

## Design Considerations

- Minimal ISR execution time.
- Blocking task notifications rather than continuous polling.
- Bounded batch buffer sizes.
- Separation of application, driver, hardware configuration and testing.
- Error propagation from I2C transactions.
- Monitoring of unexpected FIFO byte counts.
- Recovery from hardware FIFO overflow.

## Current Limitations and Future Development

- Acquired samples are decoded but not yet forwarded to an external application.
- Integration tests require manual inspection of log output.
- Recovery from interrupted I2C transactions and potential FIFO misalignment requires further development.
- Acquisition task stack usage requires formal measurement.
- Further stress testing under varying CPU loads is planned.

Future development may include telemetry transmission, sample timestamping, automated testing and more comprehensive fault recovery.
